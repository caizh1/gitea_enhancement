## 0. 先用一分钟看懂这套系统

### 0.1 两个系统分别做什么

| 系统 | 谁使用 | 主要用途 | 日常开发是否必须进入 |
| --- | --- | --- | --- |
| Gitea | 开发、测试、评审人、项目负责人 | 仓库、分支、提交、事项、Pull Request、审批、合并、发布 | 是 |
| Gitea Manager | 平台管理员、运维人员、少量仓库管理员 | Gitea 实例管理、备份恢复、定时任务、镜像、策略批量下发、提交门禁、AI Review | 通常不需要 |

一句话理解：**开发人员主要在 Gitea 工作；Gitea Manager 是管理和运维 Gitea 的控制台。**

### 0.2 开发人员每天最常走的路径

```text
领取任务
  → 从 main 拉出功能分支
  → 修改并本地测试
  → 按规则提交
  → 推送功能分支
  → 在 Gitea 创建 Pull Request
  → 处理 CI、人工评审和 AI Review 意见
  → 获得所需审批
  → 合并
  → 删除已合并功能分支
```

最常用命令：

```bash
git switch main
git pull --ff-only
git switch -c feature/ID-123-short-name

# 修改并测试后
git status
git add <文件>
git commit -m "[ID-123] feat(module): 简短说明"
git push -u origin feature/ID-123-short-name
```

然后打开 Gitea 网页，进入仓库，点击“创建 Pull Request”。不要直接向受保护的 `main` 推送。

### 0.3 上线前必须确认的版本边界

本手册根据当前两个源码工作区编写，不等于目标内网环境已经完成整套验收。

- 当前 Gitea 增强源码基于 `v1.27.3`，包含群组、继承权限、治理审计和原生审批增强。
- Gitea Manager 当前仓库中的“仓库策略中心”“外接审批规则”和“AI Code Review”部署文档，仍明确以官方 Gitea `1.26.4` 为主要适配基线。
- 因此，**不能因为 Gitea 1.27.3 和 Manager 1.26.4 相关功能分别通过测试，就宣称二者组合已经完成生产兼容验收**。
- 外接审批规则仍有 `APR-RACE-001` 等未关闭边界，当前只可作为开发或内网测试候选，不能替代生产强制门禁。
- AI Review 是辅助审查；当前模型质量不能替代人工评审、CI、分支保护或发布验收。

生产接入前，维护人员必须记录实际 Gitea 程序版本、数据库版本、Manager 包摘要、容器镜像摘要和目标实例测试结果。

# 第一部分：开发人员每天看这里

## 1. 第一次使用

### 1.1 登录和账户安全

1. 用管理员提供的 Gitea 地址、用户名和初始密码登录。
2. 第一次登录后立即修改密码。
3. 在“设置 → 安全”中启用双因素认证；保存恢复码，不要把恢复码放进代码仓库。
4. 在“设置 → SSH/GPG 密钥”中添加 SSH 公钥，或在“设置 → 应用”中创建访问令牌。
5. 令牌只授予工作所需的最小权限，不要把令牌写进代码、脚本、截图或聊天记录。

生成 SSH 密钥的常用命令：

```bash
ssh-keygen -t ed25519 -C "你的公司邮箱"
```

复制公钥内容：

```bash
cat ~/.ssh/id_ed25519.pub
```

测试连接，主机名和端口以 Gitea 页面给出的 SSH 克隆地址为准：

```bash
ssh -T -p <SSH端口> git@<Gitea主机>
```

### 1.2 找到自己有权访问的仓库

登录后可从首页“群组”或仓库列表进入项目。

- “我的群组”默认折叠，展开后可查看直接子群组。
- 点击群组名称进入群组主页；箭头用于展开下一层。
- 搜索可以找到当前账号有权访问的后代群组和仓库。
- 只被单独授予某个仓库权限时，可以进入该仓库，但不因此获得整个群组权限。
- 看不到仓库时，先确认是否登录了正确账号，再联系项目 Owner 核对授权来源和到期时间。

### 1.3 选择 HTTPS 还是 SSH

| 方式 | 适用场景 | 注意事项 |
| --- | --- | --- |
| SSH | 日常开发，推荐 | 先登记 SSH 公钥；地址中可能带非 22 端口 |
| HTTPS | 临时环境、只允许 HTTP 的网络 | 密码位置通常应使用访问令牌，不要保存明文密码 |

从仓库页面“克隆”按钮复制地址，不要凭记忆手写主机名或路径。

```bash
# SSH
git clone ssh://git@<主机>:<SSH端口>/<群组路径>/<仓库>.git

# HTTPS
git clone https://<主机>/<群组路径>/<仓库>.git
```

进入仓库后核对远程地址：

```bash
cd <仓库目录>
git remote -v
git status
```

## 2. 日常开发标准操作

### 2.1 开始一个任务

每次开始开发前，从最新目标分支创建自己的功能分支：

```bash
git switch main
git pull --ff-only
git switch -c feature/ID-123-short-name
```

推荐分支名称：

| 类型 | 示例 |
| --- | --- |
| 新功能 | `feature/ID-123-user-search` |
| 缺陷修复 | `fix/ID-456-login-timeout` |
| 文档 | `docs/ID-789-install-guide` |
| 紧急修复 | `hotfix/ID-101-data-error` |

如果项目已有其他命名规范，以仓库首页、贡献说明或项目负责人要求为准。

### 2.2 修改、检查和提交

修改过程中随时查看状态：

```bash
git status
git diff
```

提交前至少完成：

1. 只提交本任务相关文件。
2. 运行仓库要求的格式化、单元测试和静态检查。
3. 检查 `git diff --check`，避免尾随空格和冲突标记。
4. 确认没有密码、Token、私钥、数据库、构建缓存和个人配置。
5. 提交信息要能说明“改了什么”，不要只写 `update` 或 `fix bug`。

```bash
git diff --check
git add <文件1> <文件2>
git diff --cached
git commit -m "[ID-123] feat(module): add user search"
```

当前 Gitea Manager 的提交门禁示例格式是：

```text
[ID-123] type(scope): subject
```

常用 `type`：`feat`、`fix`、`docs`、`test`、`refactor`、`chore`。实际是否强制、正则表达式和错误提示以该仓库收到的服务端拒绝信息为准。

### 2.3 推送功能分支

第一次推送：

```bash
git push -u origin feature/ID-123-short-name
```

以后继续推送：

```bash
git push
```

推送被拒绝时不要连续重试，先看服务端返回的原因：

- `non-fast-forward`：远端分支有其他提交，先拉取并整理历史。
- 提交信息不合规：按门禁提示修改提交信息。
- 受保护分支：你正在直接推送 `main`，应改推功能分支并创建 PR。
- 权限不足：确认当前凭据、仓库和授权范围。
- 令牌范围不足：资源权限足够也不代表令牌权限足够，需要两者同时满足。

### 2.4 与主分支保持同步

准备提交 PR 或处理冲突前：

```bash
git fetch origin
git switch feature/ID-123-short-name
git rebase origin/main
```

发生冲突时：

```bash
# 编辑冲突文件并清理冲突标记后
git add <已解决文件>
git rebase --continue
```

放弃本次 rebase：

```bash
git rebase --abort
```

已经推送过的个人功能分支如果 rebase 改写了历史，是否允许强制更新由项目规则决定。必须使用时优先：

```bash
git push --force-with-lease
```

不要对多人共用分支或受保护分支使用强推。

## 3. Pull Request、审批和合并

### 3.1 创建 Pull Request

推送后进入 Gitea 仓库：

1. 打开“Pull Request”。
2. 点击“新建 Pull Request”。
3. 基准分支选择 `main` 或项目指定发布分支。
4. 比较分支选择自己的功能分支。
5. 标题写清任务和结果，正文说明背景、改动、测试和风险。
6. 指定评审人；需要时关联事项、里程碑和标签。
7. 创建前再次确认没有误提交敏感信息或无关大文件。

推荐 PR 正文：

```markdown
## 背景

说明为什么要改。

## 改动

- 改动一
- 改动二

## 验证

- [ ] 单元测试通过
- [ ] 页面或接口已手工验证
- [ ] 未提交密钥、数据和构建产物

## 风险与回退

说明影响范围和回退办法。
```

### 3.2 看懂合并为什么被阻止

一个 PR 可以同时受多种条件限制：

- 必须达到总审批人数。
- 指定审批群组必须分别达到人数。
- 新提交后旧审批可能失效，需要重新审批。
- CI、签名、冲突、过时分支或正式评审请求未满足。
- 受保护文件或分支规则不允许当前账号合并。
- 同一人可以满足多个指定群组要求，但在总人数中只计算一个自然人。
- 代码访问权不等于指定群组审批资格；群组审批按规则要求的直接成员资格核对。

在 PR 页面查看每条规则的实际缺口。不要通过删除保护规则、临时授 Owner 或直接改数据库来“解锁”。

### 3.3 处理人工评审意见

1. 逐条理解意见，不能确认时直接回复提问。
2. 在本地修改并重新运行相关测试。
3. 提交并推送新版本。
4. 在原讨论中说明如何处理；不适用的意见要给出证据。
5. 新提交可能使之前批准失效，等待页面重新计算。

### 3.4 看懂 AI Code Review

如果仓库已由管理员启用，PR 对话、提交或文件页标题下会显示 AI Code Review 卡片，大约每 5 秒刷新。

常见状态：

| 状态 | 含义 | 开发人员怎么做 |
| --- | --- | --- |
| 等待执行 | 已入队 | 正常等待，不要重复创建 PR |
| 分析中 | 正在读取和分析 | 可以继续人工评审 |
| 发布与核对 | 正在发布或确认评论 | 暂时不要把“未出现评论”理解为无问题 |
| 发布待核对 | 发布结果不确定 | 通知管理员核对，不要盲目重跑 |
| 已完成 | 已发布当前覆盖范围结果 | 阅读覆盖范围、跳过文件和意见 |
| 版本已过期 | PR 已有更新提交 | 以最新 SHA 对应任务为准 |
| 执行失败 | 工程链路或模型失败 | 人工评审继续；需要时通知管理员 |

重要原则：

- “没有发现问题”只代表已覆盖修改范围内没有发现证据充分的问题。
- “部分覆盖”意味着仍需人工检查未覆盖文件。
- AI 意见不是合并批准，不替代 CI、审批或安全检查。
- 对错误建议应说明原因；管理员可把有效纠正沉淀到审查经验数据集。

### 3.5 合并前最后检查

- PR 目标分支正确。
- CI 和所需检查均通过。
- 所有阻塞讨论已解决。
- 审批总人数和指定群组要求均满足。
- 当前页面对应最新 Head SHA。
- 没有未解释的 AI Review 高风险意见或未覆盖关键文件。
- 无冲突，且分支未落后到项目不允许的程度。
- 发布、迁移或配置变更已写明回退办法。

合并完成后更新本地：

```bash
git switch main
git pull --ff-only
git branch -d feature/ID-123-short-name
```

远端功能分支可在 Gitea 页面删除，或执行：

```bash
git push origin --delete feature/ID-123-short-name
```

### 3.6 开发人员常见问题速查

| 现象 | 先检查 | 正确处理 |
| --- | --- | --- |
| 找不到仓库 | 登录账号、群组路径、授权是否过期 | 联系 Owner 查看权限来源；不要申请全局管理员 |
| 能看不能推 | 角色可能是 Reporter，或共享上限只读 | 申请目标仓库 Developer；核对 Token 范围 |
| 推 `main` 被拒绝 | 分支保护 | 推功能分支并创建 PR |
| 提交信息被拒绝 | 提交门禁返回的格式 | 修改本地提交信息后再推送 |
| PR 不能合并 | 审批、指定组、CI、冲突、签名 | 在 PR 规则区域逐项处理 |
| 新提交后审批消失 | 规则要求新代码重新审批 | 修改完成后请评审人重新审批 |
| AI Review 一直排队 | Worker、模型或任务积压 | 不阻塞人工流程；通知 Manager 管理员 |
| 网页能看 PR，API 返回 403 | 当前增强版存在 Planner/共享组合 API 边界 | 临时使用网页并提交问题，不要扩大代码权限规避 |
| SSH 失败、HTTPS 正常 | SSH key、端口、客户端代理 | 从页面复制地址并运行 `ssh -vT` 取证 |
| HTTPS 反复要密码 | 使用了账号密码或凭据已失效 | 使用访问令牌并清理错误凭据缓存 |

# 第二部分：Gitea 普通用户与项目管理员

## 4. 角色、群组和权限

### 4.1 基础角色的通俗理解

| 角色 | 典型能力 | 不应默认拥有 |
| --- | --- | --- |
| Minimal Access | 看到被授权的群组基本信息 | 私有事项、PR、代码和管理权限 |
| Guest | 阅读事项，按原生规则操作自己的事项 | 私有代码读取和推送 |
| Planner | 事项与 PR 协作，具体能力按配置 | 私有代码读取和推送 |
| Reporter | 读取代码、PR、Wiki、发布，允许 clone/fetch | 推送、合并、成员管理 |
| Developer | 功能分支开发、PR、具备资格时审批和合并 | 组织成员管理、绕过保护分支 |
| Maintainer | 创建授权范围内的子群组或仓库，管理仓库设置和仓库成员 | 自动获得 Owner 的全部组织治理能力 |
| Owner | 管理本组织及其授权后代 | 管理无关组织、绕过关闭了管理员例外的分支保护 |

权限按具体能力计算，不能只比较角色名称大小。

- 多个有效授权来源按能力取并集；一个低角色不会自动覆盖另一个来源的高能力。
- 共享授权按“用户已有能力”和“共享上限”的交集生效，不会凭共享上限放大权限。
- 自定义角色是基础角色加额外能力，不能用自定义角色删除基础角色能力。
- 撤销某一来源后，如果还有团队、协作者、继承或直接授权，剩余权限仍然有效。

### 4.2 群组继承

- 父群组授权向下继承到后代群组和仓库。
- 子群组“成员”页中，同一用户显示一行；展开可看角色、来源和到期时间。
- 继承权限要回到来源群组修改，不能在子群组直接删除父级授权。
- 只有子群组权限时，不会自动获得父群组或同级群组权限。
- 仅仓库直接授权不会让用户成为整个组织成员。
- 私有父群组下创建仓库时，默认应保持私有。

### 4.3 新员工加入项目

推荐流程：

1. Owner 在正确群组发出邀请，并选择最小够用角色和到期时间。
2. 新员工使用被邀请的正确账号接受邀请。
3. 在群组成员页核对授权来源。
4. 用真实 HTTP 或 SSH 克隆一次目标仓库。
5. Developer 再推送一个功能分支并创建 PR，确认完整开发链路。
6. 尝试访问无关同级仓库，确认没有越权。

### 4.4 外部协作者

只需读取一个仓库时，优先使用单仓库 Reporter 或有到期时间的受限共享，不要把外部人员加入顶层群组。

到期或项目结束后：

1. 撤销共享、直接成员和临时令牌。
2. 用原会话重新请求，确认新请求已经拒绝。
3. 检查是否仍通过团队或其他来源保留权限。
4. 在审计记录中确认撤权对象、操作者和时间。

## 5. 仓库、分支保护与审批

### 5.1 创建仓库

在目标群组主页点击“创建仓库”。确认：

- 所属群组正确。
- 可见性正确，私有项目不要误设为公开。
- 默认分支名称符合团队规范。
- 初始化 README、许可证和 `.gitignore` 的选择符合已有代码导入方式。
- 创建人有对应 `create_project` 能力；能维护仓库不等于能在任意群组建仓库。

### 5.2 配置保护分支

路径：**仓库 → 设置 → 分支**。

建议至少保护 `main`：

- 禁止普通直接推送、强推和删除。
- 要求通过 Pull Request 合并。
- 配置所需审批人数和指定审批群组。
- 按项目需要配置过时审批处理、CI 检查、签名和正式评审请求。
- 管理员是否可以绕过要显式决定，不要依赖默认值。

当前增强版在原生分支保护页面统一编辑审批规则。弹窗中的修改先形成草稿，点击统一保存后才生效；取消不应写入。

### 5.3 指定审批群组

- 新规则只选择人员和真实群组/子群组，不把 Owner、Developer 角色名或原生 Team 当成新的治理群组。
- 新增群组审批按指定群组的直接成员计算，父群组继承成员不会自动成为该子群组审批池。
- 历史 Team ID 规则会作为兼容约束保留，不能在编辑其他字段时被静默清除。
- 分支列表只能给出候选不足提示；实际 PR 才能根据作者、提交者、当前成员资格和规则精确计算。

### 5.4 归档、转移和删除

- 归档后通常允许已有读权限继续读取，但应拒绝推送、网页写文件和合并。
- 转移仓库会改变父群组继承来源；转移后必须重新核对直接授权、共享、自定义角色和审批资格。
- 删除仓库、群组或服务器记录前先做备份，并确认镜像、Webhook、定时任务、策略模板和 AI Review 是否引用它。

## 6. Gitea 其他常用功能

### 6.1 事项

用事项记录需求、缺陷和任务。标题写结果，正文包含复现步骤、预期、实际、环境和证据。用标签、里程碑、负责人管理进度；不要用 PR 评论代替长期需求记录。

### 6.2 Wiki、发布和制品

- Wiki 适合持续维护的项目知识；与版本强相关的使用说明应随源码提交。
- Release 应对应可追溯标签，并附变更、升级、回退和校验信息。
- 上传二进制、离线包或容器包时同时提供 SHA-256。
- 下载成功不等于运行验收；必须区分包校验、目标主机启动和业务验收。

# 第三部分：Gitea Manager 管理操作

## 7. 首次登录和实例接入

### 7.1 登录

浏览器访问：

```text
http://<Manager主机>:5480
```

当前登录页只要求管理员密码，没有单独用户名。首次部署的源码默认密码是 `admin123`，生产环境不能使用。当前“系统设置”页面只有本机 IP，没有在线修改管理员密码入口；因此必须在数据库第一次初始化前，把部署配置中的 `INIT_PASSWORD` 设置成独立强密码。管理员密码一旦写入 Manager 数据库，之后只修改环境变量不会自动替换已有密码。

登录后如果页面提示“请先配置本机 IP”，先进入“系统设置”填写浏览器和被管理实例可识别的 Manager 主机地址。未配置前部分写操作会被阻止。

### 7.2 添加 Gitea 服务器

路径：**服务器管理 → 添加服务器**。

| 字段 | 说明 |
| --- | --- |
| 名称 | 便于识别的实例名称 |
| 角色 | `primary` 为备份源；`backup` 为恢复目标；`mirror` 为镜像目标 |
| 主机 IP / SSH 端口 / SSH 用户 | Manager 到 Gitea 宿主机的运维连接 |
| Gitea 端口 / URL | Gitea Web/API 地址 |
| Gitea 容器 | 实际运行的容器名，默认示例 `gitea` |
| PG 容器、数据库、用户 | 恢复和部分完整性核验使用，必须对应真实数据库 |
| API Token | 具备目标管理操作所需权限的 Token |

保存后立即点击“测试连接”。仅页面显示在线还不够，首次接入应分别验证：

1. Gitea API 可访问且版本符合预期。
2. SSH 可登录目标宿主机。
3. 运行用户有需要的 Docker 权限。
4. 容器名、数据库名和数据卷路径正确。
5. 使用一个小型测试仓库完成备份和恢复演练。

## 8. 备份、恢复和定时任务

### 8.1 手工备份

路径：**备份管理 → 创建备份**。

1. 只有角色为 `primary` 的实例会出现在源服务器列表。
2. 点击“开始备份”后等待状态从 `running` 变为 `success`。
3. 检查文件大小和 Commit 快照状态。
4. 必要时下载备份，并在独立介质保存校验值。
5. 失败时打开“错误原因”，保存首个错误和完整日志尾部，不要只重复点击。

备份成功后会采集仓库 Commit 校验集。旧备份可能显示“旧备份缺失”，不能把没有 Commit 快照的旧包当成已完成一致性证明。

### 8.2 恢复

路径：**恢复操作**。

> 恢复会停止目标 Gitea，并覆盖目标的仓库、数据库、业务数据和 `app.ini`。这是破坏性操作。

恢复前必须：

1. 进入维护窗口，停止目标业务写入。
2. 再备份一次目标现状、配置、密钥和数据库。
3. 确认选中的是正确备份和正确目标实例。
4. 确认磁盘空间、数据库容器、用户和数据路径。
5. 记录目标实例当前版本和镜像摘要。

恢复完成后：

- 查看恢复历史和“执行详情”。
- 检查每个步骤、退出码、有限长度日志和远端作业目录。
- 执行 Commit ID 验证；只有仓库数和 Commit 集一致才能记为恢复验证通过。
- 用浏览器、API、HTTP Git 和 SSH Git 做业务抽查。
- 发现 PostgreSQL 相关失败时保持维护状态，立即检查目标，不能继续开放写入。

### 8.3 定时任务

路径：**定时任务 → 创建定时任务**。

选择一个 `primary` 源和一个或多个 `backup` 目标。任务先备份源，再逐台恢复目标。

**当前调度代码使用 UTC 时间。** 中国标准时间为 UTC+8，例如希望北京时间凌晨 02:00 执行，应在当前版本中配置前一日 UTC 18:00。变更前先在测试任务中核对实际触发时间。

其他注意点：

- 后台每 60 秒扫描一次。
- 同一任务存在 5 分钟冷却窗口，运行中或冷却中不能重复启动。
- “立即执行”和自动调度共用抢占机制，不应并发执行同一任务。
- 展开任务行可以查看备份和各目标恢复步骤。
- 定期检查上次状态，不要只确认任务开关为启用。

## 9. 镜像、提交门禁和策略中心

### 9.1 Push Mirror

路径：**镜像管理 → 新建镜像配置**。

1. 选择 `primary` 源和非 `primary` 目标。
2. 当前推荐模式是 Push Mirror。
3. 选择是否 Push 后立即同步，并设置 5～1440 分钟兜底间隔。
4. 创建后等待初始化完成。
5. 在“查看详情”中检查每个仓库状态和审计记录。
6. 部分失败时只对明确失败仓库重试；“刷新/修复”用于重新核对和修复配置。

旧 Pull Mirror/Git Clone 配置已经弃用，应在核对目标数据后重新建立 Push Mirror。镜像不是备份：源端错误删除、强推或损坏可能同步到目标，仍需独立备份。

### 9.2 提交消息门禁

路径：**提交门禁**。

操作顺序：

1. 为指定 Gitea 实例创建规则。
2. 使用页面“规则测试”验证正常和异常提交信息。
3. 选择仓库并应用门禁。
4. 用真实 Git 推送一条合规提交和一条不合规提交。
5. 核对拒绝信息、仓库引用和服务端 Hook。

门禁脚本位于裸仓库的 `hooks/pre-receive.d/gitea-manager-commit-msg`。页面显示 `Hook installed` 只证明文件安装成功，不证明目标 Gitea 一定执行了该目录中的脚本。Gitea 网页编辑和 PR 合并是否经过相同 Hook，也要在目标版本真实验证。

### 9.3 仓库策略中心

路径：**仓库策略中心**。

标准流程：

```text
选择实例和组织
  → 创建空白模板或从仓库导入
  → 编辑规则并核验人员/团队
  → 选择仓库
  → 预览差异
  → 只应用可执行仓库
  → 查看执行记录和逐仓库回读结果
```

重要边界：

- 当前文档验证基线是官方 Gitea `1.26.4`；其他版本会或应被兼容检查阻止。
- 模板只创建或更新同名规则，未纳入模板的规则保留。
- 模板修改不会自动同步到仓库，必须重新预览并人工应用。
- 预览冻结本次仓库清单，后来新增仓库不会自动加入。
- “已核验成功”表示 API 有效字段回读符合预期，不等于每个真实业务行为都已执行。
- 同实例批次串行，每批最多两个仓库并发；大量仓库需要时间。
- 超时或响应丢失时系统回读判断，不应人工盲目重放写操作。

### 9.4 外接审批规则

路径：**审批规则**。

该功能当前是开发验收候选，不是生产强制审批。可以用于隔离测试：

1. 选择实例、组织、仓库和明确分支。
2. 配置总票数、稳定团队 ID 和每组票数。
3. 先执行“接入预检”，预检不修改 Gitea。
4. 仅在隔离或批准的内网测试环境导出、检查和安装组件。
5. 保留安装包和回退凭据，按安装说明分别验证页面与门禁。

`APR-RACE-001` 未关闭前，不能把轮询、展示快照或额外查询描述为严格原子审批修复，也不能宣称与 GitLab 企业版完整等价。

## 10. AI Code Review 管理

### 10.1 启用前提

- 使用独立、非管理员机器人账号。
- 机器人对所选仓库只读，但 Token 需具备读取用户、创建 Review 和评论所需范围。
- Manager 能访问 Gitea，Gitea 能回调 Manager。
- 内部 New API 地址、模型和 Key 已准备，地址在部署白名单内。
- Worker、Executor、Progress、Feedback 服务都健康。
- 目标语言、仓库规模和模型质量已经用代表性样本验收。

### 10.2 首次接入

路径：**AI Code Review → 快速接入 AI 审查**。

1. 填写内部 New API 地址和 Key。
2. 确认实际模型标识；当前默认示例为 `deepseek-v4-flash`。
3. 选择仓库，点击“检查并启用”。
4. 等待机器人、权限、Webhook 真实投递和进度组件检查完成。
5. 创建一条测试 PR，确认自动触发、状态卡片、正式 Review 和行内评论。

空仓库必须先有首个提交，才能完成 Webhook 投递验证。

### 10.3 日常管理

- “任务”查看排队、执行、发布、失败和过期记录。
- “仓库管理”启停仓库、核对机器人、Webhook 和事件时间。
- “模型与设置”调整模型、预算、超时、最大文件和意见数。
- “审查经验数据集”沉淀人工确认的误报、漏报和修正。
- `publish_unknown` 表示发布结果待核对，应先回读 Gitea 和任务记录，不能直接重跑。
- 达到预算会明确标记未覆盖，不得把部分结果写成“整个 PR 无问题”。

### 10.4 PR 进度组件

在“仓库管理”下载组件，带到 Gitea 宿主机后：

```bash
python3 install.py check --container <实际Gitea容器名>
python3 install.py install --container <实际Gitea容器名>
```

卸载：

```bash
python3 install.py uninstall --container <实际Gitea容器名>
```

安装器增量维护 Gitea CustomPath 下的模板和静态资源，并热重载模板；不应重建或停止 Gitea。CustomPath 未持久化、只读、rootless、自定义镜像或多 Web 副本环境必须先单独核验。

## 11. 安装 Gitea 增强版

### 11.1 推荐方式：已验收的 Linux amd64 离线包

当前源码仓库不保存运行镜像、数据卷、凭据或最终离线包。安装时应取得与本次发布匹配的完整交付包，并核对：

- 包文件和 SHA-256 文件。
- Linux 架构，当前交付基线为 `amd64`。
- Gitea 和 PostgreSQL 镜像摘要。
- 程序版本、数据库版本和发行说明。
- `安装并启动.sh`、Compose 文件、`.env` 示例和回退说明。

校验：

```bash
sha256sum -c <校验文件名>
```

macOS 上可使用：

```bash
shasum -a 256 <离线包文件名>
```

全新安装：

1. 在新的英文路径目录解压，不复用旧实例 Compose 项目名和数据卷。
2. 按脚本提示输入浏览器实际访问的服务器 IP 或域名。
3. 执行交付包中的：

   ```bash
   bash 安装并启动.sh
   ```

4. 保存脚本生成的随机密码和密钥，限制文件权限。
5. 等待脚本确认服务就绪，再登录检查程序版本。
6. 创建隔离测试仓库，验证网页、API、HTTP Git、SSH Git、PR、审批和受保护分支。

升级已有 Gitea：

1. 进入维护窗口并停止业务写入。
2. 完整备份数据库、Git 仓库、业务数据、原安装目录 `.env` 和 `secrets/`。
3. 记录原 Compose 项目名、数据卷、镜像摘要和程序/数据库版本。
4. 把新包解压覆盖到原安装目录，但保留 `.env`、`secrets/`、Compose 项目名和数据卷。
5. 在原目录执行 `bash 安装并启动.sh`。
6. 等待迁移完成；遇到迁移阻断时停止开放写入，保留日志和备份，不能手工修改数据库版本强行启动。
7. 迁移后不能只换回旧镜像；需要回退时恢复同一时间点的完整一致性备份。

已记录的 Demo 发行说明包含数据库 `370 → 371` 迁移，但目标实例必须以实际包和实际起始版本重新判断。

### 11.2 从源码构建

适用于开发和维护人员，不建议替代已验收发布包。

```bash
make help
make build
```

生产分发需要把前端资源嵌入单文件：

```bash
TAGS="bindata" make build
```

Linux ARM64 交叉构建示例：

## 12. 安装和升级 Gitea Manager

### 12.1 新安装前提

- Linux 主机已安装 Docker Engine 和 Docker Compose Plugin。
- 运行账号有 Docker 权限。
- 默认访问端口：前端 `5480`，后端 `5000`。
- Manager 到远程 Gitea 宿主机的 SSH 私钥已经准备，容器内只读挂载。
- `/var/run/docker.sock` 会挂入后端，等同于很高的宿主机控制权限，只允许受信任管理员使用。
- `data/` 使用可靠本地持久存储；不要把 SQLite 和任务锁放在不可靠网络文件系统。
- 已生成独立的 `SECRET_KEY`、初始管理员密码和集成服务 Token。
- 当前后端和前端 Dockerfile 默认从内网镜像仓库 `10.10.5.21:5001` 取得 Python/Nginx 基础镜像；目标机必须能访问该仓库，或已导入并正确指定等价基础镜像。
- 后端构建使用仓库内 `backend/wheels/` 离线安装 Python 依赖；前端镜像直接复制 `frontend/dist/`，源码部署前必须确认该目录是当前源码构建结果。

生成随机值的示例：

```bash
openssl rand -hex 32
openssl rand -base64 24
```

### 12.2 从当前源码部署基础 Manager

当前 `docker-compose.yml` 要求显式设置 `INTEGRATION_SERVICE_TOKEN`；`SSH_KEY_PATH` 指向的文件也必须存在。

先核对离线依赖和前端产物：

```bash
test -d backend/wheels
test -f frontend/dist/index.html
docker image inspect 10.10.5.21:5001/library/python:3.11-slim
docker image inspect 10.10.5.21:5001/library/nginx:1.31.1
```

如果目标机通过内网仓库拉取镜像，可用 `docker pull` 预检；完全离线环境应优先使用已验收的离线交付包，不要在目标机临时联网补依赖。

```bash
cd /path/to/gitea-manager
export SSH_KEY_PATH=/绝对路径/id_rsa
export INTEGRATION_SERVICE_TOKEN=<独立强随机令牌>
bash deploy.sh
```

部署脚本会创建 `data/backups`、构建镜像、启动服务并检查容器状态。

当前源码 Compose 中仍带示例 `SECRET_KEY=change-me-in-production` 和 `INIT_PASSWORD=admin123`。**生产部署前必须在受控部署配置中替换，不能原样使用。** 不要把真实值提交到仓库。

部署后：

```bash
docker compose ps
docker compose logs --tail=200 backend
docker compose logs --tail=200 frontend
```

浏览器访问 `http://<主机IP>:5480`，用首次初始化前设置的非默认密码登录，然后配置本机 IP。

### 12.3 本地开发环境

Gitea Manager 后端：

```bash
cd backend
pip install -r requirements.txt
python run.py
```

前端：

```bash
cd frontend
npm install
npm run dev
```

前端 Vite 默认在 `5173`，将 `/api` 代理到本机 `5000`。

仓库还提供隔离本地环境：

```bash
python3 scripts/local-env.py start
python3 scripts/local-env.py status
python3 scripts/local-env.py stop
```

该环境的数据、凭据和测试账号保存在 `work/本地环境` 或 Docker 命名卷中，不得进入源码或交付包。

### 12.4 升级已有 Manager

把以下三个文件放在内网服务器同一目录：

```text
gitea-manager.tar.gz
gitea-manager.tar.gz.sha256
upgrade.sh
```

先只做预检：

```bash
bash upgrade.sh --check
```

执行升级：

```bash
bash upgrade.sh
```

存在多个 Manager 时：

```bash
bash upgrade.sh --container <已有后端容器名>
```

升级器适用于 Linux x86_64 的已有 Compose 部署，会校验包、冻结相关服务、备份 Manager/Review 数据和配置、启动新服务、验证后提交；失败时尝试恢复原服务。

升级记录在原部署目录：

```text
.gitea-manager-upgrades/records/
```

这些记录可能含敏感备份，只允许部署管理员访问。若断电或 Docker 守护进程退出导致升级进程无法完成自动回退，保留执行锁和现场，根据记录恢复；不要直接删除锁、卷或数据库。

升级后如果存在 `compose.managed.json`，以后继续使用 `upgrade.sh`，不要再运行旧 `deploy.sh`。

### 12.5 安装后验收清单

- [ ] Gitea 和 Manager 登录正常；Manager 在首次初始化前已配置非默认密码。
- [ ] 实际 URL、ROOT_URL、SSH 地址和反向代理一致。
- [ ] Gitea 程序版本、数据库版本、镜像摘要已记录。

# 第五部分：日常维护与故障处理

## 13. 建议维护节奏

### 13.1 每日

- 查看 Gitea 和 Manager 容器状态。
- 查看 Manager 仪表盘、全局告警、失败备份、恢复、镜像和 AI Review 任务。
- 检查磁盘空间，特别是 Gitea 数据卷、PostgreSQL、Manager `data/backups` 和 Docker 镜像层。
- 检查定时任务是否在预期 UTC 时间执行。
- 对失败任务保存第一现场，不用重复执行覆盖证据。

### 13.2 每周

- 随机下载一个备份并校验文件可读性和 SHA-256。
- 检查备份保留策略，清理前确认文件不再被恢复任务或审计引用。
- 检查过期成员、外部协作者、长期 Token 和 SSH key。
- 查看镜像失败仓库与最近同步时间。
- 查看 AI Review Worker/Progress/Feedback 心跳和模型失败率。
- 审核管理员操作和权限变更记录。

### 13.3 每月或每次发布前

- 在隔离目标执行一次完整恢复演练。
- 用浏览器、API、HTTP Git、SSH Git 验证恢复实例。
- 验证关键仓库 Commit ID 集，而不只看页面能打开。
- 复核证书、域名、备份空间和灾备目标容量。
- 在升级前冻结版本和镜像摘要，准备书面回退步骤。
- 复核未关闭缺陷和目标环境未验收项。

## 14. 运行状态和日志

基础 Manager：

```bash
docker compose ps
docker compose logs --since=30m backend
docker compose logs --since=30m frontend
```

启用 AI Review 后，按实际 Compose 项目查看：

```bash
docker compose logs --since=30m review-worker
docker compose logs --since=30m review-executor
docker compose logs --since=30m review-progress
docker compose logs --since=30m review-feedback
docker compose logs --since=30m approval-view
```

查看 Gitea 和数据库容器：

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker logs --since=30m <Gitea容器名>
docker logs --since=30m <PostgreSQL容器名>
```

排障记录至少包含：

- 发生时间和时区。
- 操作人、账号和目标仓库。
- 页面/API/Git 的准确入口。
- 请求或任务 ID、PR 编号、分支和 Head SHA。
- 程序版本、镜像摘要、数据库版本。
- 首个错误、退出码、响应状态和相关日志时间段。
- 问题发生前后是否有升级、迁移、权限或配置变化。

日志中不要粘贴 Token、密码、私钥、完整 `app.ini` 或数据库连接秘密。

## 15. 备份体系

### 15.1 必须分别备份的对象

| 对象 | 内容 |
| --- | --- |
| Gitea | Git 仓库、LFS/附件等业务数据、数据库、`app.ini`、密钥和自定义模板 |
| Gitea Manager | `data/gitea-manager.db`、`data/backups`、部署 Compose、环境配置、SSH key 引用 |
| AI Review | Review SQLite 持久卷、`hosts.json`、主密钥、执行器令牌、相关配置 |
| 发布与升级 | 当前和上一版本镜像、离线包、SHA-256、升级记录和回退说明 |

Manager 中的“备份管理”主要备份被管理的 Gitea 实例，**不等于已经备份 Manager 自己的数据库、密钥和 Review 数据卷**。

### 15.2 一致性原则

- 数据库、仓库、配置和密钥要来自同一维护窗口。
- SQLite 使用 WAL 时要由应用支持的备份流程或停写快照保证一致，不能只复制主 `.db` 文件而忽略 WAL。
- 不要把备份目录放在被自身递归备份的数据卷中。
- 每个备份记录来源实例、时间、版本、大小、SHA-256 和验证结果。
- 备份成功的唯一可靠证明是可恢复并通过业务核验。

## 16. 安全维护

- Gitea、Manager 和数据库只向必要网络开放；优先经 HTTPS 反向代理访问。
- Manager 后端 `5000` 不应直接暴露给普通用户。
- Docker socket 只给受控 Manager 后端；一旦 Manager 管理员凭据泄露，应按宿主机高权限事件处理。
- Gitea API Token、Review 机器人 Token、模型 Key、SSH 私钥和主密钥分开管理与轮换。
- Review 机器人不能是管理员，也不能拥有代码写权限。
- 普通开发者不要进入 Manager；Manager 当前是共享管理员模式，审计不能可靠区分自然人时，应由外层运维流程补充实名审批。
- 生产禁用示例密码和默认密钥，限制秘密文件权限为仅部署管理员可读。
- 反向代理保留正确 Host、Scheme、Cookie 和客户端地址设置；升级后复核 ROOT_URL 和回调地址。
- 删除服务器记录不会自动删除历史备份/恢复记录；删除数据前分别确认审计和保留要求。

## 17. 故障处理顺序

### 17.1 Gitea 页面打不开

1. 检查容器是否运行和是否反复重启。
2. 查看 Gitea 与数据库同一时间段日志。
3. 核对端口、反向代理、证书、ROOT_URL 和数据库连接。
4. 如果刚迁移，优先查看数据库迁移错误；不要删库或改版本号。
5. 在恢复前保留数据卷和日志快照。

### 17.2 Manager 页面能开但操作失败

1. 查看浏览器返回的具体错误和后端日志。
2. 核对系统设置中的本机 IP。
3. 在“服务器管理”执行连接测试。
4. 分别核对 API、SSH、Docker socket、容器名和数据库名。
5. 确认任务是否仍在运行或冷却中。

### 17.3 备份失败

1. 查看备份记录完整错误，不要先重试。
2. 核对目标磁盘、Docker 权限、容器名和 Gitea `dump` 输出。
3. 远程实例核对 SSH 和 SFTP。
4. 确认 Manager 备份目录可写且剩余空间足够。
5. 修复首因后创建新备份，保留原失败记录。

### 17.4 恢复失败

1. 保持目标维护状态，禁止业务写入。
2. 查看恢复步骤、退出码、日志尾部和远端作业目录。
3. 区分上传校验、解压、数据库导入、文件复制、权限、启动和 Commit 验证阶段。
4. 不要在不确定状态下重复恢复覆盖现场。
5. 根据恢复前一致性备份回退，或在明确安全的步骤续查。

### 17.5 镜像失败

1. 区分 Manager HTTP 等待超时、源 Gitea Push Mirror 内部超时和目标 Gitea失败。
2. 同时查看 Manager、源 Gitea 和目标 Gitea 日志。
3. 核对远程 URL、凭据、目标可见性和仓库是否改名/删除。
4. 先对单仓库执行“重试”，再决定是否“刷新/修复”。

### 17.6 AI Review 失败

1. 检查全局开关和仓库开关。
2. 检查 Webhook 最近投递时间和目标 Head SHA。
3. 检查 Worker、Executor、Progress、Feedback 心跳。
4. 检查模型地址、白名单、Key 权限、超时和实际模型健康。
5. HTTP 200 不代表模型审查成功；仍要看 SSE/协议内容、结构化结果和执行器原始错误。
6. `publish_unknown` 先回读 Gitea 和任务状态，不盲目再次发布。

## 18. 已知限制和禁止做法

### 18.1 当前已知边界

- Gitea 增强版 1.27.3 与 Manager 高级功能 1.26.4 基线的整套现场兼容尚未由本手册证明。
- 外接审批规则仍有最终检查后撤回/移组的竞争窗口，不能生产强制启用。
- AI Review 的工程链路通过不代表内网模型质量通过。
- 多节点 Manager、网络文件系统上的 SQLite、高容量和双 24 小时稳定性不属于默认已验收范围。
- rootless、自定义 Gitea 镜像、多 Web 副本、真实移动端和全部身份源组合需要单独验收。
- 当前定时任务按 UTC 解释时间，页面未显式显示时区。

### 18.2 禁止做法

- 不要为了通过合并临时删除保护规则、授予站点管理员或直接改数据库。
- 不要把“容器 Up”“HTTP 200”“文件已下载”当成业务通过。
- 不要在响应不确定时盲目重放备份、恢复、策略下发、审批安装或 Review 发布。
- 不要删除升级锁、迁移记录、失败现场或数据卷来“快速恢复”。
- 不要把镜像同步当成不可变备份。
- 不要把生产 Token、密码、私钥、模型 Key 写进仓库和普通文档。
- 不要用当前维护机的本地缓存或日志判断另一台目标服务器已经完成索引、部署或验收。

## B. 术语

| 术语 | 说明 |
| --- | --- |
| PR / Pull Request | 把功能分支的变更请求合入目标分支 |
| 保护分支 | 限制直接推送、强推、删除和合并条件的分支 |
| 审批 | 评审人对当前 PR 版本给出的批准票 |
| 指定审批群组 | 某条规则要求必须由指定群组成员提供的票 |
| Commit 快照 | 备份时采集的仓库提交集合，用于恢复后核对 |
| Push Mirror | 由源 Gitea 向目标主动推送的仓库镜像 |
| 仓库策略模板 | Manager 中批量配置多个仓库保护规则的模板 |
| Webhook | Gitea 在 PR 等事件发生时回调 Manager 的通知 |
| `publish_unknown` | AI Review 发布请求结果不确定，需要先回读核对 |
| CustomPath | Gitea 自定义模板、静态资源等文件所在目录 |
