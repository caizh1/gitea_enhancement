# 角色、组织、权限与仓库联动测试矩阵

设计基线：`1d07c4e`；设计日期：2026-09-18。

本矩阵包含 **80 条场景，每条均有预期结果**，用于验证治理功能之间的联动，补充已有开发、Git 和 GUI 矩阵。本文件是测试设计，所有条目初始状态均为“未执行”；不以设计完成或历史样本通过宣称当前版本没有大风险。

## 一、固定测试数据与规则

| 对象 | 设置 |
|---|---|
| 组织树 | 私有顶层 `alpha` → `alpha/platform` → `alpha/platform/sdk`；同级 `alpha/business`；无关联私有顶层 `beta` |
| 仓库 | 每个组织各一个私有仓库；另设公开组织下的公开仓库、归档仓库、待删除仓库、含 PR/事项/Wiki/附件的仓库 |
| 账号 | 非成员、Minimal Access、Guest、Planner、Reporter、Developer、Maintainer、Owner 各独立账号；另外两名永久 Owner、两名审批人、一个禁用账号 |
| 自定义角色 | Reporter + `manage_approvals`；Developer + `manage_members`；Guest + `manage_group_members`；基础角色与额外能力分别记录 |
| 授权来源 | 组织直接成员、父组织继承、仓库直接成员、组织共享、仓库共享、原生 Team、协作者分别建立独立样本 |
| 仓库门禁 | `feature/*` 可正常开发；`main` 禁直接推送、强推和删除；两名有效独立审批人、最新检查通过；关闭管理员绕过 |
| 会话 | 每人独立浏览器会话、Token、SSH 密钥；管理员只准备数据和独立核验，不代替被测普通用户操作 |
| 数据隔离 | 各用例重置授权和业务状态；叠加授权必须明确列出全部来源；移组、删除、故障注入只在专用隔离实例执行 |

权限计算基线：

- 多条有效授权按**具体能力取并集**；低角色直接授权不是对高角色继承授权的显式拒绝。
- 每条共享授权先计算“受邀用户能力 ∩ 共享上限能力”，再与其他有效来源合并；仓库共享叠加组织共享时逐层受限，不能假设组织共享自动无限传递。
- 自定义角色是“基础角色能力 + 额外能力”，不能用它删除基础角色能力；角色数字不能代替能力集合。
- 有权限仍须满足 Token 范围、账号状态、归档状态、审批和分支保护等门禁。
- 成员、共享到期必须由服务端当前时间判定，不能依赖用户重新登录或浏览器刷新才生效。
- “管理仓库成员”与“管理组织成员”分开；仓库管理权不能自动变成组织管理权。

代码依据：[角色能力](../models/governance/permissions.go)、[继承和共享计算](../models/governance/membership.go)、[成员授权约束](../services/governance/member_role.go)、[自定义角色生命周期](../services/governance/group_roles.go)、[组织与迁移](../services/governance/group.go)。依据源码确定当前契约，但不能把已知缺陷当成正确预期。

当前需要特别固定的产品语义：组织共享与仓库共享对受邀方继承成员的处理不同；解除父组织归档是整树解除，不是恢复每个仓库原来的独立归档标记。相反，延迟删除后的恢复另有状态快照。测试必须区分这三种行为，不能用直觉统一预期。

### 统一执行与判定要求

1. 管理类操作分别验证**网页实际操作和 API 直接请求**；没有网页入口的能力只测 API 并注明，不虚构 UI 覆盖。
2. 所有涉及代码读取或写入的条目拆成 **HTTP+Token、SSH+用户密钥** 两条执行记录；有附件、压缩包、原始文件或 Wiki 的条目追加对应入口。
3. “读取拒绝”表示未返回私有正文、文件、对象或敏感元数据；“写入拒绝”还须证明成员、配置、授权、远端引用均没有未授权变化。
4. 每项正向测试均检查最终业务状态；不能只以按钮可见、HTTP 200 或弹出成功提示作为通过。
5. 涉及撤权必须有撤权前成功对照、撤权完成时间、旧会话新请求和独立见证。写拒绝使用真实待推送新提交；读取拒绝尽量使用撤权后生成的新内容，避免旧缓存误导。
6. 每条多角色、多来源、多状态的场景在执行时拆为原子记录。例如 `M05-parent-HTTP` 与 `M05-direct-SSH` 不能合并成一次通过。
7. 阴性请求的 403/404 可按接口隐藏资源策略不同；状态码必须符合具体接口契约且数据安全。过期版本冲突与归档拒绝应分别识别，不能把所有拒绝都误判为权限错误。
8. 本轮设计不要求 Windows/TortoiseGit；沿用用户指定跳过。GUI 主环境为 macOS，Remote-SSH 采用已验证可行的独立 Docker Linux。平台跳过不等于通过。

## 二、角色与能力边界（R01—R12）

下列基础角色均为唯一有效来源；仓库为私有。事项“管理”用修改他人事项或标签判断，不把创建自己的事项直接当作写管理权限。

| ID | 前置条件 | 测试操作 | 预期结果 |
|---|---|---|---|
| R01 | 非成员，无 Team/协作者/共享 | 搜索组织与仓库，访问详情、代码和管理 API | 私有内容及敏感管理信息不泄露；不能取得代码或修改任何数据 |
| R02 | Minimal Access | 访问获授权组织，访问事项、PR、代码和设置 | 可读取授权组织信息；不因组织可见获得私有事项、PR、代码或管理权限 |
| R03 | Guest | 查看事项、创建及编辑自己的事项；修改他人事项、读代码、推送 | 事项读取和原生允许的本人事项操作成功；管理他人事项、代码读取及推送拒绝 |
| R04 | Planner | 管理事项，读取 PR 元数据；请求 PR 文件、补丁、提交内容；克隆和推送 | 事项管理、网页及 API 的 PR 元数据读取成功；代码内容入口、克隆和推送拒绝；不得为修复 PR API 而泄露代码 |
| R05 | Reporter | 查看代码、PR、Wiki、发布；克隆；管理他人事项、推送、合并、改成员 | 允许相应读取和本地提交；写管理、远端推送、合并、成员修改拒绝 |
| R06 | Developer | 功能分支开发、PR、审批、合并；改组织和仓库成员 | 开发及具备资格的审批成功；合并仍受保护规则约束；无额外管理能力时成员管理拒绝 |
| R07 | 组织 Maintainer | 创建授权子组织/仓库，管理仓库设置和仓库成员；修改组织成员、顶层设置 | `create_group/create_project/manage_project/manage_members` 对应操作成功；缺少 `manage_group_members/manage_group` 的组织管理拒绝，不能因名称误授 Owner 能力 |
| R08 | 组织 Owner，非站点管理员 | 管理本组织及后代；管理无关联 beta；直接推送受保护 main | 授权范围内治理操作成功；beta 管理拒绝；main 仍遵守关闭绕过后的门禁 |
| R09 | 顶层授权管理者 | 创建 Reporter + 审批管理自定义角色并分配 | 获得代码读取及审批管理；不能推送、合并或管理成员；基础 Reporter 能力不丢失 |
| R10 | 自定义角色创建者没有 `manage_group` 或没有准备授出的某能力 | 调用创建/更新角色 API，添加 Owner 级能力或未知能力字符串 | 无管理权、超出自身能力或未知能力的请求拒绝；角色和已有成员权限不变 |
| R11 | 在用自定义角色，基础角色保持不变 | 增加再移除额外能力，用原会话操作本级与后代资源 | 增加后合法操作成功；移除后新请求拒绝；基础能力保留；全部引用同一角色的授权同步生效 |
| R12 | 自定义角色分别被成员、未过期邀请引用；另有未使用角色 | 删除角色或修改其基础角色；解除引用后再操作 | 在用角色的删除/基础角色修改拒绝，引用不损坏；解除所有有效引用后的合法修改或删除成功；无悬空权限 |

## 四、成员、邀请与授权生命周期（M01—M12）

| ID | 前置条件 | 测试操作 | 预期结果 |

| M03 | Guest + `manage_group_members`，但无代码写能力及 `manage_group` | 给别人或自己授 Developer/Owner，修改已有 Owner | 超出操作者能力的授权拒绝；不能借成员管理间接升权；无组织管理能力时不能修改 Owner |
| M04 | 同一用户先为 Reporter，再升 Developer，再降 Reporter | 不退出原会话，逐次读取、推送和访问成员管理 | 升级后普通写入成功；降级后新写入拒绝但读取保留；不会凭旧页面保留写权限 |
| M05 | 父组和仓库直接授权均为 Developer | 先撤父组，再撤直接授权；反向顺序另测 | 撤一条后另一条仍可写；最后一条撤销后新读写请求拒绝；成员页面解释剩余来源 |
| M06 | 原生 Team、协作者、治理成员并存 | 分别移出 Team、删除协作者、删除治理成员 | 每步仅移除对应来源；剩余有效能力保留；全部来源撤销后无幽灵权限 |
| M07 | 成员有固定到期时间，使用旧 Token/SSH/网页会话 | 到期前、边界时刻、到期后发起新请求；再检查后台任务前后 | 到期前允许，到期后拒绝；不等待到期清理任务才鉴权；无其他来源时不继续显示为有效成员 |
| M08 | 只有一条能保障组织管理的永久 Owner 来源 | 删除、降级或改为会过期授权；再以两名永久 Owner 作对照 | 会导致没有永久 Owner 的请求拒绝且回滚；保留另一名永久 Owner 时合法变更成功；继承和原生 Owners 来源按实际规则计算 |
| M09 | 待接受邀请 | 正确账号接受；接受前访问；错误账号/邮箱接受；重复接受 | 接受前无成员权限；身份匹配后只取得邀请声明范围与角色；错误身份拒绝；重复请求不重复授权或扩大权限 |
| M10 | 邀请分别已过期、撤销、拒绝；另有邀请者在接受前失去管理权 | 使用旧邀请链接/令牌接受 | 无效邀请不能创建成员；邀请者失权后重新校验授予资格，不能以旧邀请绕过当前授权；失败不留下半条成员记录 |
| M11 | 开启访问申请，申请者无成员权 | 提交、撤回、拒绝、批准；用无管理权账号或申请者本人批准 | 申请本身不授权；合法批准后按批准角色生效；无权批准拒绝；撤回/拒绝/重复批准不产生意外授权 |
| M12 | 成员账号被禁用；另有停用前有效邀请、共享、审批 | 保持旧会话尝试访问及管理；重新启用后再测 | 禁用期间所有用户身份的新访问与写入被拒绝；授权记录存在不代表账号有效；重新启用仅恢复仍有效授权，不复活已撤销来源 |

| S09 | 开启禁止外部共享；准备同根和跨根目标 | 新增跨根共享、修改请求目标 ID；合法同根共享作对照 | 跨根新增或改目标绕过限制的请求拒绝；合法范围成功；不得只靠前端隐藏按钮。现有共享是否追溯撤销按已声明设置契约单独记录 |
| S10 | 组织 A 共享给 B、B 共享给 C；用户仅为 C 直接成员；另设仓库共享给 B | 访问 A/B 组织资源及单独共享仓库；试自身共享、反向成环和重复创建 | 组织共享不无限转授，C 用户不能仅凭两跳组织共享访问 A；仓库共享对可计算的 B 有效授权再次取交集。自共享/循环拒绝；重复关系不重复授权 |

## 六、仓库创建、迁移、归档与删除（P01—P12）

| ID | 前置条件 | 测试操作 | 预期结果 |

| P02 | 用户只管理 platform | 篡改 owner、组织 ID 或路径在 beta 创建仓库 | 拒绝且 beta 无新仓库；不得通过请求体绕过目标组织校验 |
| P03 | 同名仓库位于不同组织；同组织已存在目标名 | 新建同名、大小写变体、非法名称 | 不同命名空间合法同名不串数据；同命名空间冲突拒绝；非法路径不能越目录或覆盖已有仓库 |
| P04 | 无组织代码权限，仓库直接 Developer | 访问该仓库、组织其他仓库、组织成员与设置 | 目标仓库可正常开发；不自动成为组织成员或取得邻近仓库/组织管理权限 |
| P05 | 仓库私有/公开两种状态，公开父组和私有父组分别测试 | 合法调整可见性，使用旧链接和匿名会话访问 | 公开转私有后新匿名读取拒绝；私有转公开须有权且符合祖先约束；权限切换不遗留私有内容匿名入口 |
| P06 | 仓库已有 PR、事项、保护规则、成员、共享 | 合法改名，使用新旧路径访问及推送 | 稳定资源 ID、业务数据、授权和保护规则保持；别名访问仍按当前权限；列表、导航、克隆地址一致 |
| P07 | 有权转出且满足目标接收/建库要求，另有无目标权账号 | 跨组织转移仓库；目标同名冲突对照 | 合法转移完整成功；缺源/目标必要权限或名称冲突时完整拒绝；不发生仅移动数据库或仅移动 Git 的半成功 |
| P08 | P07 仓库有旧父组继承、直接成员、共享、自定义角色 | 转移后逐来源核对并用原会话读写 | 旧父组继承失效，新父组继承生效；显式授权按迁移契约保留；跨根自定义角色正确映射且能力不丢失/放大；邀请和申请不指向旧对象 |
| P09 | Developer 有写权，仓库有可合并 PR | 归档仓库后 clone/fetch、push、网页/API写文件、合并 | 原有读授权仍可读；各写入口拒绝，引用/PR/配置无未授权变更；恢复后按当前权限恢复写入 |
| P10 | 父组及后代状态混合，部分仓库原本已归档 | 归档父组，撤销一成员，再恢复父组 | 后代写入被阻止；归档期间允许合法撤权。按当前明确规则，解除父组归档会解除整棵树归档，包括此前独立归档仓库；独立待删除仓库仍只读；被撤成员不复活。影响预览须准确提示范围 |
| P11 | 有删除管理权，配置延迟删除窗口 | 标记仓库/组织删除，再在窗口内恢复；到期清理前后核对 | 待删除状态可追踪且阻止业务写入；恢复保留代码、PR、事项和原有效状态；不能通过恢复让已撤授权复活 |
| P12 | 专用可销毁仓库、待删除组织；有权与无权账号 | 确认永久删除、无权删除、过期请求重放；重新创建同名资源 | 只有满足权限和删除状态条件的请求执行；关联数据按契约清理；新资源采用新身份和授权，旧链接、邀请、令牌引用不得将旧权限转嫁给新对象 |

|---|---|---|---|
| X01 | 混合直接、继承、共享授权及无权私有仓库 | 首页、组织仓库列表、搜索、分页、总数、详情和仓库列表 API 对照 | 同一用户的资源集合与单项访问一致；先按权限过滤再分页；无漏项、重复项或无权资源计数泄露 |

## 九、真实业务组合场景（E01—E08）

以下每行是一个完整用户流程，仍需逐步记录结果；链路中任何必要步骤未完成，该行不能算业务闭环通过。

| ID | 前置条件 | 测试操作 | 预期结果 |
|---|---|---|---|
| E01 | 新员工未加入任何组织 | Owner 邀请加入 platform Developer → 接受 → 找到 sdk 仓库 → 开发 → PR → 审批合并 | 用户能完成交付；继承来源清楚；父级、同级、beta 不扩权；最终代码和审计正确 |
| E02 | 员工同时有父组、Team、协作者和共享来源 | 执行“只移出某组”，再执行“完全离职撤权”两种流程 | 移出某组只移除其来源，剩余权限正确显示；完全离职清除所有有效来源并禁用账号后，旧会话新请求不能读写；已有本地文件不算远程越权 |
| E03 | 外部供应商需要短期只读一个仓库 | 建共享、限制 Reporter、设置到期 → 读取 → 尝试写入 → 到期访问 | 期间仅目标仓库可读不可写；到期后新请求拒绝；不可读其他项目、管理成员或继续传播更高权限 |
| E04 | 产品规划人员 Planner | 创建和管理事项 → 查看 PR 元数据 → 与开发协作 → 请求代码和补丁 | 规划协作闭环正常，网页和 API 一致；私有代码不因 PR 协作而泄露；已有 CAP-PR-001 必须单独回归 |
| E05 | 仓库负责人只管理一个仓库 | 配置保护/审批、添加低权限成员、完成发布；尝试修改组织或任意授 Owner | 授权范围内管理闭环成功；不能修改组织成员、越过自身授予上限或绕过审批发布 |
| E06 | 团队从 alpha 调整到 beta，存在直接成员、共享、角色、待接受邀请和打开的 PR | 移组/转移 → 新旧成员验证 → 接受有效邀请 → 继续 PR | 数据完整、路径一致、授权按新组织重新计算；显式保留来源可解释；审批策略和候选资格重算，不把旧组织审批/权限无条件沿用 |
| E07 | 项目暂停，成员持续变化 | 归档组织 → 撤成员/共享 → 申请写入 → 恢复组织 → 继续开发 | 暂停期写入被拒绝，必要治理撤权可执行；按当前整树解除归档策略恢复后合法成员可交付，失权者仍拒绝；独立删除计划不被清除 |
| E08 | 项目退役，含后代仓库和外部共享 | 延迟删除 → 核验影响 → 窗口内恢复；另一个样本完成永久删除 → 同名重建 | 恢复样本保留应保留的数据和当前授权；永久删除仅作用目标树；重建样本不继承已删除资源的成员、共享、邀请或下载权限 |

## 十一、执行顺序与风险判定

优先执行能造成跨组织越权、间接提权、组织失管和数据损坏的用例：R10、M03、M08、O02、O06—O09、S04—S10、P02、P07—P12、X02、X06—X08、C01—C07。随后执行全部合法管理与业务闭环，防止只证明“拒绝有效”，却漏掉正常用户不能工作。

每条执行记录至少包含：基线/配置、实际身份、全部授权来源、对象 ID 与路径、前置 revision、操作入口与协议、预期、实际结果、前后数据/引用、权限变更时间、脱敏截图/日志、缺陷编号。性能样本另记规模、资源限制、并发数和耗时。

| 结论 | 判定要求 |
|---|---|
| 通过 | 所有必要断言有证据，允许操作完成业务目标，拒绝操作证明没有私有数据泄露或未授权变更 |
| 失败 | 实际结果违反明确预期；先排除错误前置、凭据串号、未等状态完成、脚本误选等执行器问题 |
| 未验证/跳过/不适用 | 独立标注理由，不计通过；“没有按钮”不能自动证明 API/Git 安全 |
| 阻塞风险 | 仅已证实的 P0/P1 导致 `VERDICT: FAIL`；必须给出当前可达触发、完整因果链、严重影响和反证结果 |
| 无已证阻塞 | 完成约定审查后若 P0/P1 为空，`VERDICT: PASS`；同时明确未验证边界，不能解释为绝无风险 |

本文件暂不出 PASS/FAIL：本轮是测试设计，尚未执行这 80 条联动场景。
