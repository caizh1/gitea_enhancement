## 2. 固定数据与操作规程

### 2.1 环境

| 对象 | 准备要求 |
|---|---|
| 组织 | `alpha` → `alpha/platform` → `alpha/platform/sdk`；同级 `alpha/business`；无关联 `beta` |
| 私有仓库 | 上述每个组织各一个仓库，命名为 `dev-root`、`dev-platform`、`dev-sdk`、`dev-business`、`dev-beta` |
| 补充仓库 | `dev-public` 公开；`dev-archive` 归档；`dev-assets` 包含 LFS 文件及指向独立私有仓库的子模块 |
| 内容 | 每仓库使用不同的非敏感识别文本；记录初始提交 SHA、文件摘要，避免读错仓库也判成功 |
| 分支 | `feature/*` 普通分支；`main` 禁直接推送、强推和删除，只允许经 PR 合并 |
| PR 门禁 | 两名独立有效审批人；禁止作者自批；追加提交使旧审批失效；最新提交状态检查 `acceptance/check` 必须成功；关闭管理员绕过 |
| 标签 | 普通标签 `test-*`；受保护标签 `release-*`，仅明确指定发布账号可创建、更新和删除 |
| 身份 | 每个基础角色独立账号；另设第二开发者、两位审批人、发布账号、无成员账号及自定义角色账号 |
| 凭据 | 每账号独立 Token、SSH 密钥、浏览器会话和工作目录；不得继承管理员凭据或全局凭据助手 |
| 客户端 | 固定客户端执行全矩阵；macOS、Windows、Remote-SSH Linux 执行跨平台复验；记录实际发起 Git 的主机 |

管理员仅准备配置和提供只读见证；状态检查由独立检查账号按记录的提交 SHA 上报。普通用户不能借用检查账号。展示路径不保证等于 Git 路径：从仓库页面/API 取得真实 HTTP 与 SSH 克隆地址，分别记录，不手工推测子组织 URL。

每条用例从独立快照或等效重新初始化的数据开始。默认只有该用例声明的授权；开始前列出治理直接、继承、共享、原生 Team、协作者、管理员和部署密钥来源。B08/B09 等叠加用例例外。撤权后测试不得重新登录或清空原会话。

### 2.2 可复用步骤

| 步骤 | 执行与证据 |
|---|---|
| 读取 | 使用被测账号搜索、打开详情、调用仓库列表及内容 API；分别 clone、fetch，核对仓库识别文本和提交；拒绝读取时使用全新目录，旧克隆 fetch 前在远端增加新识别提交 |
| 开发 | clone 后新建 `feature/<执行编号>`，修改英文名文件、写入中文测试内容，commit 并记录 SHA；push 后由独立见证账号读取对应引用，再全新 clone 核对 SHA 和内容 |
| 拒绝推送 | 先确认目标仓库和引用存在、同一请求在有权对照条件下可成功；以被测身份推送有实质变化的新提交；保存退出码与错误，并由见证账号对比全部受影响引用 |
| 撤权 | 保留原克隆及凭据，保存授权变更提交成功的响应与时间；先验证仍有其他来源时的保留权限，再撤销全部来源；重新发起远程读取和写入 |
| PR | 用户推送功能分支、创建 PR；两人分别审批；检查账号为最新 SHA 报成功；有权用户合并；独立读取目标分支，核对内容、提交关系、PR 状态与审计身份 |
| 恢复 | 按用例恢复权限或服务，保留用户本地提交；重新发起操作证明可以继续工作，不用重新创建用户掩盖恢复问题 |

本地 `commit` 不依赖服务器授权；已下载内容不能因撤权被收回，不把本地可读判为泄露。拒绝读取要求没有取得撤权后的新私有内容。拒绝写入必须核实远端，不以按钮隐藏、HTTP 状态码或客户端超时单独作结论。401/403/404 等具体表现按入口记录，但服务故障、错误地址、凭据未配置不能算权限拒绝通过。

协议规则：所有远程 Git 场景分别执行 HTTP(S)+Token 与 SSH+用户密钥；部署密钥仅适用 SSH，Token 范围仅适用 HTTP(S)，在记录中解释不适用，不能算通过。网页与 API 分别记录，不把 Git 通过推及其他入口。

### E. PR 与审批合并

| ID | 前置条件 | 用户步骤 | 预期与关键断言 |
|---|---|---|---|
| E01 | 两位直接有效审批人；检查成功 | 完成 PR 步骤 | 目标内容正确、提交关系与合并方式一致；PR 与审计对应实际操作者 |
| E02 | 分别审批不足、检查失败 | 分别网页、API、自动合并入口合并 | 目标不更新；排队不等于已合并 |
| E03 | 同一人属于两个审批组；保留两名独立人数门禁 | 此人审批一次再合并 | 不能满足两名独立审批人；补第二人后可继续 |
| E04 | 仅继承父组角色，不是指定子组直接成员 | 对该子组审批规则投票并尝试合并 | 不自动成为子组审批池的有效票；直接成员对照有效 |
| E05 | 已完成审批与检查 | 追加提交后合并；再为新提交补齐审批及检查 | 旧状态不能放行；最新提交满足门禁后成功 |
| E06 | PR 已获审批，main 随后变化 | 合并原 PR；重新取得当前门禁后再合并 | 校验新目标和有效审批，不沿用旧判定；目标内容正确 |
| E07 | 分别撤销审批人资格、合并人权限 | 用旧页面或原 API 请求合并 | 按最新资格拒绝失效授权；引用不变 |
| E08 | 分别作者自批、重复审批、无权编辑规则 | 尝试满足或降低门禁 | 不能替代独立审批；规则无未经授权变化 |
| E09 | 允许私有 Fork；用户可在 Fork 开发 | Fork 开发、提上游 PR、直接推上游 | Fork 授权不授予上游直接写权；上游 PR 按门禁合并 |

E03 保留独立人数门禁，避免误把一个人满足不同规则的资格与满足两个人混为一谈。E09 若实例明确禁用私有 Fork，则记录该配置和阻止行为，Fork 开发闭环仍记未验证，不虚报成功。

### F. 并发、中断与客户端

| ID | 前置条件 | 用户步骤 | 预期与关键断言 |
|---|---|---|---|
| F01 | 隔离实例；能控制鉴权后与引用更新前暂停点 | 暂停 push，发起撤权，记录各自提交顺序，再恢复 | 撤权先完成则不能以旧权限写；写事务先完成则撤权后新请求必须拒绝；互相等待时检查无死锁 |
| F02 | 隔离实例；合并门禁检查后暂停 | 分别撤销审批、审批成员、合并人，恢复合并 | 按线性化顺序验证，不以失效授权放行；不能仅靠随机重试证明 |
| F03 | 分别 push/merge；引用更新前后两个阶段 | 分别断网、停止服务进程，恢复并对账 | 引用、PR、授权事务与审计可对账；未提交可恢复，已提交不重复；不凭超时判断失败 |
| F04 | 两名用户同时操作同一目标 | 分别并发推送、并发合并 | 无提交丢失、无静默覆盖、无重复成功业务状态 |
| F05 | macOS、Windows、Remote-SSH Linux | 各执行 E01 完整链路、D06 保护拒绝、C06 撤权拒绝 | 各自两协议独立证据；Linux 检查远端扩展宿主实际 Git 与凭据 |
| F06 | clone 后离线；服务器撤权 | 离线 commit，上线 push，再恢复权限重推 | 本地提交保留；撤权期间远端拒绝；恢复后同一工作可交付 |

并发测试必须保存暂停点位置、服务端关联标识、事务开始/完成与引用更新顺序。仅观察客户端墙钟不足以证明原子性。若现有测试设施无法提供确定性暂停点，记录缺口，不修改生产 Hook 或将随机碰撞通过当作完成。

### G. 图形化 Git 客户端推送与拉取

本组指桌面或 IDE 内的 Git 图形界面；Gitea 网页编辑属于 D09。必测客户端为 VS Code 源代码管理界面与 Windows TortoiseGit。VS Code 覆盖 macOS、Windows 本地及 Remote-SSH Linux 工作区；TortoiseGit 覆盖 Windows 本地。两者分别记录结果，不互相代替验收。若实际团队使用其他图形化客户端，应按其名称和版本另行复制执行记录；未取得该客户端环境不得宣称已兼容。

#### 图形客户端执行范围

| 客户端 | 环境与必测场景 | 独立记录要求 |
|---|---|---|
| VS Code | macOS、Windows：G01～G10、G12；Remote-SSH Linux：G01～G12 | 记录窗口所属工作区、实际 Git 执行主机和凭据来源 |
| TortoiseGit | Windows：G01～G10、G12；G11 不适用 | 每个适用场景分别执行 HTTP(S) 与 SSH；记录 TortoiseGit、Git for Windows 版本与实际 SSH 客户端配置 |

TortoiseGit 操作要求：

- 从资源管理器菜单进入克隆、提交、拉取、推送及同步等界面；菜单名称以安装版本和语言为准。首次推送核对本地分支、远程分支及跟踪关系，避免推错仓库或分支。
- G03 分别验证获取与拉取；G04/G05 在实际冲突编辑界面解决冲突并标记完成，再继续合并或变基，核对未提交内容和双方提交均保留。
- G08/G09 记录 HTTPS 凭据助手及 Windows 凭据缓存的实际来源。界面显示的提交作者不能代替服务器认证账号；切换账号后通过服务端证据确认身份。
- SSH 记录实际配置的客户端及密钥加载方式，包括使用 OpenSSH，还是 TortoiseGitPlink/PuTTY 与 Pageant；按目标环境真实配置执行，不假定它与终端使用相同密钥或 agent。不同 SSH 配置如需声明支持，分别执行并留证。
- G10 的同步界面分别保留拉取、推送的操作结果与日志；有未推送提交时不得仅依据对话框关闭判为同步成功。G12 恢复后刷新日志与远程引用，确认是否已经提交。
- TortoiseGit 执行编号增加客户端标识，例如 `G09-SSH-sdk-Developer-revoked-Windows-TortoiseGit`；与 Windows VS Code 记录分开统计。没有 Windows 实机执行证据时标为未验证。

被测用户必须通过界面完成克隆、分支选择、暂存、提交、拉取和推送。命令行仅用于独立见证、准备数据及诊断，不代替图形界面操作。每例分别使用 HTTP(S)+Token、SSH 密钥；保存操作前后分支、远程地址、跟踪分支、传入/传出提交状态、提示截图和脱敏 Git 输出。按钮名称以实际客户端版本为准。同步按钮可能组合拉取和推送，须分别记录两阶段结果。

## 4. 执行顺序、拆分与验收

实测判定补充：原生 `read_issues` 允许创建普通事项，作者可以编辑自己的事项；`write_issues` 对应事项管理能力。C04 使用修改他人事项及添加标签验证能力交集，不能把创建自己的事项返回 201 直接判为越权。原始错误断言及反证均保留在实测证据中。

1. 准备数据并保存初始授权、保护规则、引用快照；确认合法对照请求成功。
2. 先执行 A06、B01、D06、E01；基础链路失败时记录首因，相关用例记阻塞未验证。
3. 执行 A～E 和 G，其后执行 F；每个破坏性用例恢复独立初始数据，避免串扰。
4. 按 [执行记录模板](user-development-permission-record.md) 记录证据、反证与统计。

执行编号采用 `场景-协议-目标-角色-变体-平台`，例如 `B01-SSH-sdk-Developer-inherited-macOS`。网页/API 入口分别编号；原生 Team 与协作者、撤销与到期、读与写、多个并发暂停点分别记录。拆分后的总数在执行前冻结，不以 70 行代替实际实例数。

统计口径：

- 执行覆盖率＝已完成判定实例数 / 计划内适用实例数；失败属于已执行，阻塞和未验证不属于已执行。不适用需写理由并独立列数。
- 正向成功率＝符合预期的允许实例数 / 已执行允许实例数；同时列出计划内允许实例的覆盖率，防止选择性执行。
- 越权放行数量＝预期拒绝却取得受限内容或产生未授权变更的实例数。
- 合法操作误拒绝数量＝前置条件与有效授权均确认，但业务操作被错误拒绝的实例数。
- 人工投入分别记录准备、执行、判读、复测分钟数；没有同一固定样本的人工基线对比，不宣称减少人工 80%。

报告必须区分验收完成度和代码审查结论。P0/P1 需具有当前支持范围内可达路径、完整因果链、严重影响及代码/确定性证据，并经过保护机制、调用约束和恢复方式反证。仅成立的 P0/P1 导致 `VERDICT: FAIL`；完整审查后无阻塞项才写 `VERDICT: PASS`。未开展审查时写“审查未执行”，不得自动产生 PASS。P2/P3 和未验证风险分别列出，不影响审查结论，但 PASS 不代表未执行场景已验收。
