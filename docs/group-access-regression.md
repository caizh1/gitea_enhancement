# 审批主体与继承仓库修复报告

发布修订：1.27.3-demo.20260916.4；程序：1.27.3+governance.demo.r5；数据库：371。

## 首次复现

使用独立 PostgreSQL 与旧 r3 镜像，建立私有顶层群组、子群组及私有仓库，分别只向顶层赋予六个测试用户 Minimal Access、Guest、Reporter、Developer、Maintainer、Owner 角色。

- 审批表单存在原生团队选择器，来源是 Gitea Team 数据，包含自动生成的 Owners；与真实群组选择器并列，造成角色与群组混淆。
- Reporter、Developer、Maintainer、Owner 能访问子组导航及仓库详情，但 `/api/v1/user/repos` 均遗漏该仓库。原生仓库搜索只纳入协作者、团队、原生组织关系，没有纳入治理成员的继承来源。
- Minimal Access 不提供代码读取能力，不能为了让仓库出现而统一扩大所有角色权限。用户现场具体角色及页面尚未获得补充信息，本报告对应上述明确复现场景。

## 修复

- 审批表单只选择人员与真实群组／子群组；原生 Team 不再作为新审批规则候选。Owner、Developer 仍是成员角色，不创建同名审批组。
- 新增规则的审批群组沿用既有直接成员计票；角色继承不自动把父组成员计入子组审批池。
- 既有规则的 Team ID 保留在保存数据中，界面标注历史审批要求，避免修改名称、人数时静默清空旧门禁。旧原生总人数规则仍作为兼容要求；新增群组审批要求使用“添加审批规则”。
- 原生仓库搜索在分页前根据当前有效治理能力补齐候选，同时保留关键词、所有者、单元、私有性及分页限制；搜索、统计和 ID 查询使用同一准备步骤。
- 已撤销的“创建团队”顶部入口不随本包恢复；不删除旧团队数据和已有授权。

## 验证

- models/repo、services/governance 测试通过；新增继承仓库搜索、统计、分页 ID 及撤销回归通过。
- 原生分支审批与首页完整路径集成回归通过。
- 最终 r5 Linux amd64 镜像的 PostgreSQL 实例复验：四种有代码访问权的标准角色均出现在个人仓库列表。
- 浏览器使用仅在顶层获 Developer 的普通用户登录：首页显示仓库，点击进入可见代码文件与 README。
- 真实 HTTP 与 SSH Git 读取成功；撤销顶层成员后，两种协议均拒绝，仓库列表移除，详情接口返回 404。
- 浏览器打开审批弹窗，只有人员与真实群组／子群组，选项展示完整路径；取消操作正常。
